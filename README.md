# 封包迷宮 Packet Maze — 規格書

> 一個在瀏覽器裡玩「晶片內網路（Network-on-Chip）路由」的互動沙盒：
> 親手弄壞連線，看封包怎麼繞路、在哪裡卡住。

## 1. 動機與目標

多核心晶片的核心之間用格狀網路（2D Mesh）傳遞封包。路由演算法決定封包怎麼走，
而當某些連線故障時，有的演算法會直接卡死，有的能繞過去。這些概念用文字講很抽象，
但只要「點一下弄壞一條線，看封包撞上去」就一目了然。

**目標使用者**：修計算機結構／晶片網路課的學生、對路由演算法好奇的人。
**一句話目標**：30 秒內讓人看懂「為什麼需要容錯路由」。

## 2. 功能需求

| # | 功能 | 說明 |
|---|------|------|
| F1 | 格狀網路 | 可選 4×4 ～ 8×8 的 Mesh，節點為路由器，相鄰節點以連線相接 |
| F2 | 設定起訖點 | 以「起點／終點」切換鈕決定點擊節點時要設哪一個；設完起點自動切到終點 |
| F3 | 製造故障 | 點擊任一連線即可切換「正常 ⇄ 故障」（故障以紅色虛線表示） |
| F4 | 隨機故障 | 以滑桿設定故障率（0–30%），一鍵隨機產生故障 |
| F5 | 選擇演算法 | XY 維度順序路由、West-First 轉向模型、容錯最短路徑（BFS） |
| F6 | 封包動畫 | 封包逐跳移動並留下軌跡；被擋住時在故障處顯示 ✕ |
| F7 | 單次結果 | 顯示送達／失敗、實際跳數、最短曼哈頓距離、繞路多走幾跳 |
| F8 | 三方比較 | 每次發送後，列出同一組起訖點下三種演算法各自的結果 |
| F9 | 大量測試 | 隨機送 300 個封包，以長條圖比較三種演算法的送達率與平均跳數 |
| F10 | 速度調整 | 滑桿調整動畫速度 |
| F11 | 主題 | 自動跟隨系統深／淺色，並可手動切換 |

## 3. 演算法定義

- **XY 路由**：先沿 X 方向走到目標欄，再沿 Y 方向走。完全固定、不會死結，但路上任一連線壞掉就失敗。
- **West-First**：若需往西，必須先把西邊走完；之後在東／南／北中挑「有前進效果且沒壞」的方向（優先剩餘距離較大者）。屬部分自適應、只走最短路徑。
- **容錯最短路徑（BFS）**：知道整張網路的故障狀態，找出避開故障的最短路線。當作「理想上限」的參考線，實際硬體很難做到。

## 4. 非功能需求

- 單一 `index.html`，CSS 與 JavaScript 內嵌，不依賴任何外部函式庫或網路資源。
- 用 SVG 繪製，桌機與手機（約 375px 寬）都能操作，不出現水平捲動。
- 打開檔案即可使用，可直接放上 GitHub Pages。

## 6. 設計決策紀錄（與 AI 討論後的取捨）

- **為什麼選三種演算法？** XY 代表「最簡單」，BFS 代表「最理想」，West-First 落在中間，三者並列最能看出差異。
- **為什麼用切換鈕設定起訖點，而不是右鍵？** 手機沒有右鍵與 Shift。
- **為什麼 West-First 只走最短路徑？** 保持與教科書定義一致；也正好呈現「部分自適應仍會被擋」。
- **為什麼大量測試固定 300 個封包？** 數量足以讓比例穩定，又能瞬間算完。

## 7. 驗收標準

1. 無故障時，三種演算法皆 100% 送達，且跳數等於曼哈頓距離。
2. 在 XY 路徑上弄壞一條線，XY 失敗並在該處顯示 ✕，BFS 仍能送達。
3. 故障率 20% 時，大量測試的送達率應呈現 XY ≤ West-First ≤ BFS。
4. 在手機寬度下所有按鈕可點、網路圖完整顯示。

## 8. 部署

將 `index.html` 放在 repository 根目錄，於 Settings → Pages 選擇 `main` 分支 `/ (root)` 發布。
